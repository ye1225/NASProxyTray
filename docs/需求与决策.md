## 记录格式

```
### R【编号】 · 【一句话标题】

- **提出时间**：【YYYY-MM-DD】
- **原文**：【用户原话，尽量不改写 —— 原话里常藏着没被注意的约束】
- **我的理解**：【转成可执行的描述；有歧义就写清两种解释】
- **验收标准**：【怎么算做完了，要能验证】
- **状态**：【待澄清 / 待做 / 进行中 / 已完成 / 未完成（原因） / 已砍掉（原因）】
- **相关决策**：【技术选型或取舍，写清「为什么不选另一个」】
```

**四条规矩**：

1. **一次只问一个问题**，问清了再记；分不清的一律标「待澄清」，**不许猜**
2. 需求收集结束时，**把清单复述一遍请用户确认**，确认后再进架构设计
3. 被砍掉、被打断的需求**也要留**，写清为什么 —— 否则下一个人会重新提一遍
4. 验证结论要**实测支撑**，不写「应该没问题」

### 2026-09-23 · 笔记本（首次接手，v1.0.0 现状）

#### R1 · 四项总目标：拆模块 / 单 exe / 4K 显示 / 可升级

- **提出时间**：2026-09-23
- **原文**：「我有 4 个目标：优化应用逻辑（主脚本 1000 行，拆模块）／打包成单 exe（现在必须带
  lib/ 和 ui/）／4K 分辨率显示优化／可升级架构（检查更新）」
- **我的理解**：四条独立可验收的工程目标，不是功能需求。核心诉求是**把能用的脚本变成能给
  别人用的软件**。
- **验收标准**：① 主脚本拆成模块且行为不变；② 只发一个 exe，用户不用带 `lib\` 与 `ui\`；
  ③ 200% 缩放下界面与菜单不虚不大；④ 程序能自己发现新版本。
- **状态**：**已完成**（四条全落地，见 `HANDOFF.md`「四个目标的完成情况」）
- **相关决策**：D1 模块化方式、D2 界面选型、D3 打包方式、D5 DPI 方案、D10 更新检查形态

#### R2 · 运行时数据不要落在 exe 同级目录

- **提出时间**：2026-09-23
- **原文**：「运行时会在 exe 同级目录生成很多文件和文件，需要解决，能否统一放到 c 盘固定位置。」
- **我的理解**：绿色版程序却在自身目录拉一堆文件，导致 exe 无法自由移动/改名，且用户看着乱。
  诉求 = **exe 做到纯粹的可执行文件，状态全部外置到用户数据目录**。
- **验收标准**：干净目录下首次运行 exe，同级目录不产生任何新文件；日志、配置、WebView2 缓存、
  更新记录都在 `%LOCALAPPDATA%\NASProxy\`；从旧版升级时自动迁移并清理遗留。
- **状态**：**已完成**（v1.2.1）
- **相关决策**：D4 数据目录位置

#### R3 · 托盘右键菜单字体特别大（高 DPI）

- **提出时间**：2026-09-23
- **原文**：「桌面图标右键菜单 dpi 不对，文字特别大。」（附图两张）
- **我的理解**：高 DPI 下菜单文字异常放大。**注意这与 R1 的第 3 条不是同一件事** —— R1 是
  「界面发虚（欠缩放）」，R3 是「菜单文字过大（过缩放）」，两个方向相反，根因也不同。
- **验收标准**：200% 缩放下菜单文字与常规程序一致，不巨大。
- **状态**：**已完成**（v1.2.0/v1.2.1）
- **相关决策**：D5 —— 根因是 **point 字体被手工又乘了一次 DpiScale**（GDI+ 已随 DPI 自动放大），
  已把「point 字体不乘 DpiScale、只有 Padding 这类物理像素值才乘」定为硬规则

#### R4 · 【环境约束，非功能需求】360 拦截程序

#### R5 · 导入第三方 PAC 后，本来能打开的 Google 打不开了

- **提出时间**：2026-09-23
- **原文**：「我上传了这个项目的 pac 文件，反而能打开的 google 网站打不开了：
  https://github.com/zhiyi7/gfw-pac」
- **我的理解**：这是**用户主动报的 bug**，且症状很有诊断价值 ——「国内站正常、Google 全挂」
  指向「命中了代理规则，但代理地址不可用」。
- **根因**：网上的现成 PAC 把代理地址**写死成作者本机的**（gfw-pac 第一行是
  `PROXY 127.0.0.1:3128`）。它只表达「哪些域名走代理」，「代理在哪」是作者按自己环境填的。
- **验收标准**：导入任意第三方 PAC 后，命中规则的域名走**用户自己配的**代理地址；方案关键字
  （`PROXY`/`SOCKS`/`DIRECT`）原样保留；`DIRECT` 与 `http://host:port` 不被误改。
- **状态**：**已完成**（v1.2.2）
- **相关决策**：D7 自动替换代理地址；可关（配置项 `pacRewrite`，缺省视为 `true`）

#### R11 · 界面一直显示「保存中」

- **提出时间**：2026-09-23
- **原文**：「一直显示保存中」（附图）
- **我的理解**：R10 引入的**回归 bug**，用户当天就发现了。这类「改完立刻回归」的节奏说明
  改交互必须同时想清楚**状态机**。

- **验收标准**：保存一次即停，状态条能回到正常；异常时不会永久卡住。
- **状态**：**已完成**（v1.2.6，含 5 秒看门狗清 `saveInFlight`）
- **相关决策**：D8 —— 并把这条定为**生死攸关的不变量**写进 `HANDOFF.md`

#### R14 · exe 的窗口圆角有锯齿

- **提出时间**：2026-09-24
- **原文**（按日志）：「用户报：exe 的窗口圆角边缘有锯齿。」
- **我的理解**：debug 直跑正常、**exe 里才有的问题** —— 这类「只在打包后才出现」的差异
  必须用 exe 复现，不能只看源码。
- **根因（两个，都是硬货）**：① ps2exe 生成的 exe 没有 supportedOS 清单 → .NET 兼容 shim
  把 OS 报成 **6.2 (Win8)** → `$osBuild -ge 22000` 永远为假 → **exe 从 v1.0.0 起就没走过
  DWM 圆角路径**，一直走 1-bit region 回退；② 纯无边框窗口必须加 `WS_THICKFRAME`，
  DWM 才肯画圆角（否则 `DwmSetWindowAttribute` 返回 0 但视觉不生效）。
- **验收标准**：exe 与 debug 行为一致；DWM 圆角属性回读 = 2；圆角边缘有抗锯齿过渡像素。
- **状态**：**已完成**（v1.2.7，过渡像素实测 **0 → 1719**）
- **相关决策**：D9 —— 用 `ntdll!RtlGetVersion` 拿真实 build（`Environment.OSVersion` 不可信）

## 决策记录

影响面大的技术决定单独记在这里（需求之外的架构级选择）。

### D1 · 模块化方式：靠文件名排序，不靠模块清单

- **时间**：2026-09-23
- **背景**：主脚本 1366 行要拆，但两种运行模式（开发直跑 / 打包成单文件）必须行为一致。
- **备选方案**：A. PowerShell 模块（`.psm1` + `Import-Module`）——正式但要维护清单，
  且打包后路径语义变；B. **按 `src\NN-name.ps1` 文件名排序 dot-source** —— 零配置，顺序即约定。
- **决定**：**B**
- **理由**：加载顺序**只有一个来源**（文件名），开发与打包两条路径不可能分叉。模块间只用
  `$script:` 变量通信，**禁止依赖 `$PSScriptRoot`**（dot-source 后它指向模块自身）。
- **代价**：编号即契约，插入模块得挑号（`00/10/…/90` 之间留了空号）；不能享受 PowerShell
  模块的导入缓存等特性。

### D2 · 界面选型：WebView2 + HTML，而不是纯 WinForms

- **时间**：2026-09-23（v1.2.0）
- **背景**：v1.0.0 用纯 WinForms 画界面，改样式极慢、观感受限。
- **备选方案**：A. 继续 WinForms；B. **WebView2 承载 HTML/CSS**；C. WPF。
- **决定**：**B**
- **理由**：界面能用 HTML/CSS 快速迭代（这次 600ms 自动保存、三色图标、对勾尺寸都在前端一改
  即见效）。宿主只负责窗口、DPI 换算和消息分发。
- **代价**：**多一个外部依赖**（WebView2 Runtime）→ README 必须写清安装方式，旧 Win10 可能缺；
  前端异常会静默失败 → 已约定把前端异常以 `[UI-ERROR]` 写进 `ProxyTray.log`。

### D3 · 打包成单 exe：先压缩再 Base64 内嵌，运行时释放

- **时间**：2026-09-23（v1.2.0）
- **背景**：R1 要求「只发一个 exe，不必带 `lib\` 与 `ui\`」。
- **备选方案**：A. 把资源直接 Base64 内嵌 —— 体积膨胀 33%；B. **先压 ZIP 再 Base64**；
  C. 用自解压外壳。
- **决定**：**B**，ps2exe 必须 `-noConsole -STA -x64`
- **理由**：压缩后整个 exe 只有约 463 KB，比当时估的 10–15 MB 小两个数量级。
- **代价**：① 首次运行要释放到 `runtime\<版本>\`，用**先临时目录再整体改名**避免留半个残缺目录；
  ② **解压必须手工逐条写字节**，不能用 `Expand-Archive`（后者会给 DLL 打上「来自 Internet」
  标记）；③ **绝不能给 ps2exe 加 `-DPIAware` / `-winFormsDPIAware`**（会把 DPI 感知写进 exe
  清单，反而让运行时无法升级到 Per-Monitor V2）。

### D4 · 运行时数据目录：`%LOCALAPPDATA%\NASProxy`

- **时间**：2026-09-23（v1.2.1）
- **背景**：R2。
- **备选方案**：A. exe 同级；B. `%APPDATA%`（漫游）；C. **`%LOCALAPPDATA%`**。
- **决定**：**C**
- **理由**：配置/缓存/日志是**绑定本机的**，不需要漫游；用 LocalAppData 让 exe 可以随便移动改名。
- **代价**：旧版本在 exe 同级留下的文件要主动清理，得写一段迁移逻辑；用户想找配置时路径稍隐蔽
  （已在 README 写明）。

### D5 · 高 DPI：Per-Monitor V2，且 point 字体不再手工乘 DpiScale

- **时间**：2026-09-23（v1.2.0/v1.2.1）
- **背景**：R1-③（界面发虚）与 R3（菜单文字过大）同时存在，方向相反。
- **决定**：声明 Per-Monitor V2；`Form.DeviceDpi` **必须先建句柄再读**；前端 `size` 消息给的是
  **CSS 像素**，宿主乘 `DpiScale` 后才 `SetBounds`。
- **理由**：GDI+ 渲染 **point 字体已随设备 DPI 自动放大**，再乘一次就是双重放大 ——
  **v1.2.0 菜单文字巨大正是这个原因**。只有 Padding 这类**物理像素**值才需要手工乘。
- **代价**：**别信注册表判 DPI**（`LogPixels` 与 `PerMonitorSettings\*\DpiValue` 都可能是切换
  缩放后的陈旧值）；要精确值走 `shcore.GetDpiForMonitor(MDT_EFFECTIVE_DPI)`。

### D6 · PAC 分流：`direct-list` 为默认策略，且用哈希表 O(1) 判定

- **时间**：2026-09-23（v1.2.3）
- **背景**：R7。
- **备选方案**：A. `proxy-list`（老行为：命中清单才走代理）；B. **`direct-list`**（命中清单直连，
  其余走代理）。
- **决定**：**B**
- **理由**：境外站是**无限集**，国内站是**有限集** —— 枚举有限的那边更现实，且符合 R7
  末句「我的代理自己会过滤」。
- **代价**：清单漏判会让国内站多绕一趟（可接受，代理会再判一次）；实现上**必须**用
  哈希表 + 后缀逐级查找，**不能**写成逐条 `dnsDomainIs` 线性扫描（700 条就是 700 次比较）；
  判定写 `CHINA_DIRECT[cand] === 1` 而非真值判断（避开 `constructor`/`toString` 原型链 key）。

### D7 · 第三方 PAC 的代理地址自动替换

- **时间**：2026-09-23（v1.2.2）
- **背景**：R5。
- **决定**：`Convert-PacProxyEndpoint` —— 只换「地址:端口」，方案关键字原样保留；
  配置项 `pacRewrite` 缺省视为 `true`，关掉就完全保留原文件。
- **理由**：第三方 PAC 表达的是「哪些域名走代理」，代理地址必须用**用户自己的**。
- **代价**：正则有踩坑点 —— 替换串里的 `$` 会被当成**反向引用**（先 `.Replace('$','$$')`），
  且必须用 `[regex]::Replace` 静态方法**不能**用 `-replace`；正则要求「方案 + 空白 + host:port」，
  这样 `DIRECT` 与 `http://host:port` 不会被误改。

### D8 · 自动保存：600ms 防抖，且「发出请求的瞬间必须清 dirty」

- **时间**：2026-09-23（v1.2.5 / v1.2.6）
- **背景**：R10 主动砍掉保存按钮；R11 是它引入的回归。
- **决定**：600ms 防抖自动保存 + 校验不过不发请求 + 5 秒看门狗清 `saveInFlight`。
- **理由**：R11 的无限循环根因就是 `flushSave()` 没在发请求时清 `dirty` → 宿主的 `saved`
  回执被当成「期间又有改动」→ 无限补保存。这是**生死攸关的不变量**：改动时置 `dirty=true`、
  **发出请求的瞬间置 `dirty=false`**。
- **代价**：状态机比按钮复杂（多一个看门狗）；前端异常必须落日志（`[UI-ERROR]`），
  否则界面卡住时无从查起。**查界面问题先看 `ProxyTray.log`**。

### D9 · 窗口圆角：DWM 合成 + `WS_THICKFRAME` + WndProc 子类化

- **时间**：2026-09-24（v1.2.7）
- **背景**：R14 —— exe 圆角锯齿；debug 正常，只有打包后暴露。
- **备选方案**：A. 维持 `SetWindowRgn` 1-bit 裁剪（锯齿源头）；B. **DWM 合成圆角**。
- **决定**：**B**，并配套子类化：`WM_NCCALCSIZE` 返 0、`WM_NCHITTEST` 恒返 `HTCLIENT`。
- **理由**：A 是 1-bit 掩码，**必然**有锯齿；DWM 是真正的抗锯齿合成。但 DWM 对纯无边框窗口
  **返回 0 却不生效**，必须加 `WS_THICKFRAME`（加完客户区会缩进 7px，所以必须配子类化抵消）。
- **代价**：① 得用 `ntdll!RtlGetVersion` 拿真实 build —— ps2exe exe 的
  `Environment.OSVersion` 谎报 6.2（Win8），导致 **v1.0.0 起从没走过 DWM 路径**；
  ② 建句柄后**要尽早**调用（Opacity=0 阶段改样式不闪），且每次核对 `WS_THICKFRAME`
  是否还在（防 WinForms `RecreateHandle` 丢状态）；③ Win10 / DWM 失败时仍回退 region 路径。

### D11 · 隐私去化必须改提交历史，不能只改当前文件

### D12 · 文档分层：一句话该放哪一层，只看「换个项目还成立吗」

- **时间**：2026-09-24（R16 / R18 / R21）
- **背景**：`HANDOFF.md`、跨项目 `MEMORY.md`、项目 `.workbuddy\memory\` 三份文档容易互相抄。
- **决定**：按**适用范围**分层，**一处只说一次**：

| 内容 | 写在哪 | 入库 |
| --- | --- | --- |
| 跨项目通用经验、铁律、流程、环境坑 | `D:\WorkBuddy\MEMORY.md` | 否 |
| 用户长期固定要求 | 同上，「用户对我的固定要求」一节 | 否 |
| 项目架构、约定、构建发布、**当前范围与结论** | `<项目>\HANDOFF.md` | **是**（公开前脱敏） |
| **需求原话与逐条决策**（含被砍的） | `<项目>\docs\需求与决策.md`（本文件） | **是** |
| 该项目本机细节、命令备忘 | `<项目>\.workbuddy\memory\MEMORY.md` | 否 |
| 逐日工作流水 | `<项目>\.workbuddy\memory\YYYY-MM-DD.md` | 否 |

- **理由**：判断方法就一句 —— **把这句话搬到另一个完全不同的项目里，还成立吗？** 成立 → 上层；
  不成立 → 项目层。两处若都写，早晚互相矛盾，且**不可能同时维护**。
- **代价**：写东西前要先想清层级，比「随手记在哪就算哪」慢一点；但它避免了双真相源，
  交接时只有一处需要更新。

### D13 · 三层记忆的分工与去向

- **时间**：2026-09-24（R19 / R20 / R23）
- **背景**：用户问 memory 要不要上传 GitHub。
- **决定**：**不进主仓库**。三层各有归属：
  ① **云端记忆 + 历史对话检索** —— 账号级，换机器自动就在，**无需同步**；
  ② **用户级记忆 `~\.workbuddy\MEMORY.md`** —— 只放**指针**（内容在 `D:\WorkBuddy\MEMORY.md`），
  避免两份互相矛盾；
  ③ **项目 `.workbuddy\memory\`** —— 本机细节，**不入库**，靠 NAS 整包同步（R22）跨机器。
- **理由**：跨机器 ≠ 公开。要用**私有通道**解决跨机器，而不是把私有内容塞进公开仓库。
  而且要警惕：`.gitignore` 里那条「助手工作目录（本地记忆/任务，不入库）」是**有意的**，不是漏的。
- **代价**：memory 的备份依赖用户手动上 NAS（目前**无自动备份**，是真风险）；
  `~\.workbuddy\skills\` 与用户级记忆在 **C 盘**、不在 `D:\WorkBuddy\` 里，**搬目录带不过去**
  → 已把它们的**源**放进 `_工具\` 随包走，并有 `装到本机.ps1` 负责落回 C 盘。

### D14 · 跨机器必须整包 zip 传输，不能逐个文件丢 NAS

- **时间**：2026-09-24（R22）
- **背景**：用户打算手动把 `D:\WorkBuddy` 同步到 NAS。
- **决定**：**打包成一个 zip 再传**，并用开工/收工脚本做两道校验闸。
- **理由**：**NAS 是 Linux 文件系统** —— 它**大小写敏感**，`README.md` 与 `readme.md` 会变成
  两个文件，回到 Windows 只有一个能活；文件名里的 `: * ?` 也会被改名。而且手动复制是**无脑覆盖**，
  两台机器都改过时谁后搬谁赢，另一边**永久消失**（`.workbuddy\memory\` 不在 git 里，GitHub 救不了）。
- **代价**：多两个步骤（收工打包 / 开工解压）；包里有 `.git`（这是**故意**的，git 历史是接续的
  一部分）；**打包时必须排除 `_归档\` 自己**，否则会把正在写的 zip 包进去。
